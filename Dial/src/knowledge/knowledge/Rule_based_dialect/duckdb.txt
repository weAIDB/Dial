**Title**: 1.1 Alias Definition and Reference

**Content**:  
DuckDB supports alias definition in SELECT clauses using the optional AS keyword or by direct assignment (omitting AS), consistent with standard SQL. However, unlike MySQL—which uses backticks (`) to quote identifiers—DuckDB uses **double quotes (")** to delimit identifiers that contain spaces, special characters, or reserved keywords. Single quotes in DuckDB are strictly for string literals and **cannot** be used to define aliases; attempting to do so results in a syntax error, not silent misinterpretation as in MySQL.

**CRITICAL Differences / Dialect Features**:  
- **Quoting mechanism**: DuckDB uses double quotes (`"alias name"`), whereas MySQL uses backticks (`` `alias name` ``).  
- **Single quotes**: In MySQL, `SELECT salary 'Annual Salary'` is syntactically valid but returns a string literal instead of an alias—a common pitfall. In DuckDB, this would cause a **syntax error**, as single quotes cannot serve as identifier delimiters.  
- **Case sensitivity**: DuckDB treats all identifiers (including quoted ones) as **case-insensitive** (unlike PostgreSQL, which treats quoted identifiers as case-sensitive). However, it preserves the original casing in output unless `preserve_identifier_case = false` is set.  
- **Reserved keywords**: Aliases that match SQL keywords must be quoted with double quotes in DuckDB (e.g., `"SELECT"`), similar to MySQL’s requirement for backticks.

**DuckDB Syntax Examples**:
```sql
-- Standard alias (AS optional)
SELECT first_name AS fn, last_name ln FROM employees;

-- Quoted alias with space/special chars
SELECT salary AS "Annual Salary" FROM employees;
SELECT id AS "id-field!" FROM employees;

-- Using reserved keyword as alias (must be quoted)
SELECT 123 AS "SELECT";  -- valid

-- Invalid: single quotes for alias (syntax error in DuckDB)
-- SELECT salary 'Annual Salary' FROM employees;  -- ❌ Not allowed
```

Thus, while both systems support explicit/implicit aliasing and require quoting for non-standard identifiers, they differ fundamentally in quoting syntax, handling of single quotes, and case-sensitivity behavior.

**1.1 Alias Definition and Reference**

DuckDB supports column aliasing using the standard SQL `AS` keyword, and also allows omitting `AS` (implicit aliasing). For aliases containing spaces, special characters, or reserved keywords, DuckDB requires **double quotes (`"`)**—not backticks—as identifier delimiters. Unlike MySQL, **single quotes in DuckDB are strictly for string literals** and cannot be used to define aliases; attempting to do so results in a syntax error, not silent misinterpretation as a string.

**Key Differences vs. MySQL:**
- **Quoting**: DuckDB uses double quotes (`"Alias Name"`) for delimited identifiers; MySQL uses backticks (`` `Alias Name` ``).
- **Single quotes**: In DuckDB, `SELECT salary 'Annual Salary'` is **invalid syntax** and throws an error. MySQL parses this as a string literal adjacent to a column (implicit concatenation), which leads to unexpected results—but DuckDB does not allow this.
- **Prefix alias syntax**: DuckDB uniquely supports an alternative alias syntax using colons (`res: col1 + col2`), which is not valid in MySQL.

**DuckDB Syntax Examples:**
```sql
-- Standard alias with AS
SELECT first_name AS fn, last_name AS ln FROM employees;

-- Implicit alias (without AS)
SELECT first_name fn FROM employees;

-- Alias with space using double quotes
SELECT salary AS "Annual Salary" FROM employees;

-- Prefix-style alias (DuckDB-specific)
SELECT
    "Annual Salary": salary,
    full_name: first_name || ' ' || last_name
FROM employees;

-- Invalid in DuckDB (syntax error):
-- SELECT salary 'Annual Salary' FROM employees;  -- ❌ Not allowed
```

> **CRITICAL**: Unlike MySQL, DuckDB enforces stricter parsing: single quotes never define aliases, and identifier quoting uses SQL-standard double quotes instead of MySQL’s backticks. This avoids MySQL’s pitfall of silently returning a string instead of an aliased column.

**Title**: 1.2.1 String Literal

**Content**:  
In DuckDB, string literals are **exclusively delimited by single quotes (`'`)** and produce values of the special `STRING_LITERAL` type, which can be implicitly converted to any other data type (e.g., DATE, INTEGER). Unlike MySQL, **double quotes (`"`) are never used for string literals** in DuckDB—they are reserved strictly for quoted identifiers (e.g., column or table names), and using them for strings results in a parser error.

**CRITICAL Differences / Dialect Features**:
- **Unlike MySQL**, which allows double-quoted strings in non-ANSI modes (though discouraged), **DuckDB forbids double quotes for strings entirely**—they always denote identifiers.
- DuckDB supports **dollar-quoted string literals** (`$$...$$` or `$tag$...$tag$`), a PostgreSQL-style feature **not available in MySQL**, which is especially useful for strings containing quotes or newlines.
- DuckDB allows **implicit concatenation of single-quoted string literals** *only* when separated by whitespace that includes **at least one newline**—adjacent single-quoted strings without a newline cause a syntax error. MySQL does not support implicit concatenation at all.
- DuckDB supports **escape sequences** (e.g., `\n`, `\t`) via **`e'...'` prefixed literals**, whereas MySQL uses backslash escapes by default (configurable via `NO_BACKSLASH_ESCAPES` SQL mode).
- To include a single quote inside a string, both systems use doubling (`''`), consistent with standard SQL.

**DuckDB Syntax Examples**:
```sql
-- Standard single-quoted string (correct)
WHERE name = 'John Doe';

-- Double quotes cause error (identifier, not string)
-- WHERE name = "John Doe";  -- ❌ Parser Error

-- Dollar quoting (MySQL does not support this)
SELECT $$It's "easy" to embed quotes!$$;

-- Tagged dollar quoting
SELECT $abc$Contains $$ and ' and " $abc$;

-- Escape sequences with e-prefix
SELECT e'Line 1\nLine 2';

-- Implicit concatenation (requires newline)
SELECT 'Hello'
    ' World';  -- ✅ Valid → 'Hello World'

-- This fails (no newline):
-- SELECT 'Hello' 'World';  -- ❌ Syntax error
```

**Title**: 1.2.2 Identifier Quoting (Object Names)

**Content**:  
DuckDB handles identifier quoting using **double quotes (`"`)** rather than MySQL’s backticks (`` ` ``). Unquoted identifiers in DuckDB must adhere to standard SQL rules: they cannot be reserved keywords, cannot start with a digit or special character, and cannot contain whitespace. If any of these conditions are violated—such as using a keyword like `SELECT` as an alias—the identifier must be quoted.

Unlike MySQL, **DuckDB does not allow unquoted use of reserved keywords** as object names. For example, `SELECT name, group FROM users;` would fail in DuckDB just as it would in MySQL if `group` is a keyword, but the quoting mechanism differs: DuckDB requires `"group"`, not `` `group` ``.

**CRITICAL Differences / Dialect Features**:  
- **Quoting character**: DuckDB uses double quotes (`"identifier"`), whereas MySQL uses backticks (`` `identifier` ``).  
- **Case sensitivity**: DuckDB treats **all identifiers as case-insensitive**, including **quoted identifiers**—a notable divergence from most SQL databases (like PostgreSQL, which treats quoted identifiers as case-sensitive). For example, `"Group"` and `"group"` refer to the same column.  
- **Identifier preservation**: By default, DuckDB preserves the original casing of identifiers in output (e.g., `AS CosineOfPi` appears as `CosineOfPi` in results), but comparisons remain case-insensitive. This behavior can be disabled via `SET preserve_identifier_case = false;`, forcing all identifiers to lowercase.  
- **Escaping quotes**: To include a double quote inside a quoted identifier, DuckDB uses SQL-standard escaping by doubling the quote: `"IDENTIFIER ""X"""` represents an identifier named `IDENTIFIER "X"`.

**DuckDB Syntax Examples**:
```sql
-- Valid: quoting a keyword
SELECT "name", "group" FROM "users";

-- Valid: quoted identifier with space
SELECT "user id" FROM "my table";

-- Escaping double quotes in identifier
SELECT "column ""with"" quotes" FROM "data";

-- Case-insensitivity in action (succeeds)
SELECT col_A FROM (SELECT 'x' AS col_a);

-- Using a reserved keyword as alias (requires quotes)
SELECT 123 AS "SELECT";
```

In summary, while both MySQL and DuckDB require quoting for non-standard identifiers (e.g., keywords, special characters), they differ fundamentally in quoting syntax, case handling, and treatment of quoted identifiers.

**Title**: String Case Sensitivity

**Content**:  
In DuckDB, string comparisons are **case-sensitive by default** because the default collation is `BINARY` (also aliased as `C` or `POSIX`). This means that `'hello' = 'HeLLo'` evaluates to `false`. To perform case-insensitive comparisons, DuckDB provides the `NOCASE` collation, which can be applied per-expression using the `COLLATE` clause, set globally via `SET default_collation = NOCASE`, or defined at the column level during table creation.

Unlike MySQL—where case insensitivity is the default behavior for non-binary collations and case sensitivity is explicitly triggered with the `BINARY` operator—DuckDB defaults to case-sensitive comparisons and requires explicit opt-in for case insensitivity.

DuckDB also supports combining collations (e.g., `NOCASE.NOACCENT`) and offers ICU-based locale-specific collations when the ICU extension is loaded, enabling advanced linguistic sorting and comparison rules.

**CRITICAL Differences**:  
- **Default behavior**: MySQL is typically case-insensitive by default (depending on collation), while DuckDB is **case-sensitive by default** (`BINARY` collation).  
- **Syntax**: MySQL uses `BINARY` as an operator (`expr BINARY = value`) to enforce sensitivity; DuckDB uses `COLLATE` clauses to specify comparison rules.  
- **Flexibility**: DuckDB allows fine-grained control via per-expression, per-column, or global collation settings, and supports collation chaining (e.g., `NOCASE.NOACCENT`), which has no direct equivalent in MySQL.

**DuckDB Syntax Examples**:
```sql
-- Default: case-sensitive
SELECT 'apple' = 'APPLE';  -- returns false

-- Case-insensitive via COLLATE
SELECT 'apple' COLLATE NOCASE = 'APPLE';  -- returns true

-- Set global default collation
SET default_collation = NOCASE;
SELECT 'apple' = 'APPLE';  -- now returns true

-- Column-level collation
CREATE TABLE fruits (name VARCHAR COLLATE NOCASE);
INSERT INTO fruits VALUES ('Apple');
SELECT * FROM fruits WHERE name = 'APPLE';  -- matches 'Apple'
```

**Title**: 2.4 Boolean Type: Representation of Abstract Logic  
**Content**:  
DuckDB natively supports the `BOOLEAN` data type (with alias `BOOL`), which strictly represents logical truth values: `true`, `false`, and `NULL` (for unknown). Unlike MySQL—where `BOOLEAN` is merely an alias for `TINYINT(1)` and treats any non-zero integer as `TRUE`—DuckDB enforces a true three-valued Boolean logic compliant with standard SQL semantics.

In DuckDB, Boolean values are primarily generated through comparisons (e.g., `i > 10`) or logical expressions, and they cannot be implicitly converted from arbitrary integers. For example, inserting or casting an integer like `5` directly to `BOOLEAN` will result in an error unless explicitly handled via comparison or conditional logic.

Boolean literals `true` and `false` are case-insensitive keywords in DuckDB and can be used directly in queries. The `WHERE` and `HAVING` clauses filter rows based on strict Boolean evaluation: only rows where the condition evaluates to `true` are retained; `false` and `NULL` results are excluded.

**CRITICAL DIFFERENCES**:  
- **Unlike MySQL**, DuckDB does **not** treat `BOOLEAN` as an integer type. There is **no implicit conversion** from numeric values to Boolean.  
- DuckDB adheres to **standard SQL three-valued logic** (`true`, `false`, `NULL`), whereas MySQL’s Boolean behavior is tied to integer storage and coercion rules.  
- In MySQL, `SELECT TRUE` returns `1`; in DuckDB, it returns the literal `true`.

**DuckDB Syntax Examples**:
```sql
-- Valid Boolean literals
SELECT true, false, NULL::BOOLEAN;

-- Boolean from comparison
CREATE TABLE integers (i INTEGER);
INSERT INTO integers VALUES (5), (15), (NULL);
SELECT * FROM integers WHERE i > 10;  -- Returns only 15

-- Logical operations follow three-valued logic
SELECT true AND NULL;  -- Returns NULL
SELECT false OR NULL;  -- Returns NULL
```

**Title**: 2.4.2 BIT Type Handling Differences  
**Content**:  
DuckDB supports a `BITSTRING` type (aliased as `BIT`) that represents variable-length sequences of 1s and 0s. Unlike MySQL’s `BIT(1)`, which stores a single bit but often exhibits confusing behavior, DuckDB’s `BITSTRING` is more transparent and flexible—it behaves like a string of bits with no implicit padding by default.  

**CRITICAL**: Unlike MySQL, DuckDB does **not** use fixed-width storage based on a declared size (e.g., `BIT(8)`). Instead, `BITSTRING` is variable-length, similar to a binary string. However, DuckDB provides the `bitstring(value, length)` function to explicitly left-pad a bitstring to a desired width—something MySQL lacks as a built-in convenience. Additionally, DuckDB allows direct casting from integers and strings to `BITSTRING`, automatically converting numbers to their full binary representation (e.g., `123::BITSTRING` yields a 32-bit zero-prefixed string), whereas MySQL requires functions like `BIN()` or literals like `b'1111011'`.

**DuckDB Syntax Examples**:  
```sql
-- Cast string to BITSTRING (no padding)
SELECT '101010'::BITSTRING AS b;

-- Create fixed-length bitstring with left-padding
SELECT bitstring('0101011', 12) AS b;  -- Result: '000000101011'

-- Cast integer to BITSTRING (32-bit representation by default)
SELECT 123::BITSTRING AS b;  -- Result: '00000000000000000000000001111011'
```

**Title**: 2.4.2 BIT Type Handling Differences

**Content**:  
DuckDB implements bit manipulation through its `BITSTRING` type, which is fundamentally different from MySQL’s `BIT(n)` type. In DuckDB, a bitstring is an explicit data type that represents a sequence of bits (e.g., `'1010'::BITSTRING`). Unlike MySQL, DuckDB does **not** have a fixed-width `BIT(n)` storage type that behaves like a binary integer; instead, it treats bitstrings as variable-length sequences of 0s and 1s, manipulated via dedicated operators and functions.

**CRITICAL**:  
- **Unlike MySQL**, DuckDB does not use `BIT(1)` to store a single-bit value in a numeric or binary context. Instead, it uses the `BITSTRING` type for all bitwise operations, and literals must be explicitly cast (e.g., `'1'::BITSTRING`).  
- DuckDB **does not support** MySQL-style bit literals like `b'1'` or `0b1`. Bitstrings are written as quoted strings followed by `::BITSTRING`.  
- All bitwise operations (`&`, `|`, `xor`, `~`, `<<`, `>>`) require operands to be of type `BITSTRING`, and for binary operators (`&`, `|`, `xor`), the bitstrings **must be of equal length**—a stricter requirement than MySQL’s implicit padding or truncation behavior.  
- DuckDB provides rich built-in functions (`bit_count`, `get_bit`, `set_bit`, etc.) and aggregate functions (`bit_and`, `bit_or`, `bitstring_agg`) that have no direct equivalent in MySQL.

**DuckDB Syntax Examples**:
```sql
-- Bitwise AND (equal length required)
SELECT '10101'::BITSTRING & '10001'::BITSTRING;  -- Result: 10001

-- Create a 7-bit string from a shorter one (left-padded with zeros)
SELECT bitstring('1010'::BITSTRING, 7);  -- Result: 0001010

-- Count set bits
SELECT bit_count('1101011'::BITSTRING);  -- Result: 5

-- Extract bit at index 2 (0-based from left)
SELECT get_bit('0110010'::BITSTRING, 2);  -- Result: 1

-- Aggregate distinct integers into a bitstring
SELECT bitstring_agg(id) FROM (VALUES (1), (3), (5)) AS t(id);
```

**Title**: 4.3.1 Sequence or Auto-increment Mechanism

**Content**:  
DuckDB implements auto-incrementing identifiers using **standalone sequence objects**, created via the `CREATE SEQUENCE` statement. Unlike MySQL’s column-bound `AUTO_INCREMENT`, DuckDB sequences are independent database objects that generate numbers via the `nextval('sequence_name')` function. These sequences can be used as `DEFAULT` values in table columns to emulate auto-increment behavior.

**CRITICAL Differences / Dialect Features**:  
- **Unlike MySQL**, DuckDB does **not support an `AUTO_INCREMENT` column property**. Instead, it relies on explicit sequence objects and the `nextval()` function.
- Sequences in DuckDB are **first-class schema objects**, supporting advanced features like custom start values, increments (including negative for descending), min/max bounds, and optional cycling (`CYCLE`).
- MySQL ties auto-increment strictly to a single table column; **DuckDB sequences can be shared across multiple tables** or used independently.
- DuckDB requires manual integration of sequences into tables via `DEFAULT nextval('seq')`, whereas MySQL handles this implicitly.
- DuckDB provides `currval()` to inspect the last value obtained from a sequence in the current session—**a feature absent in MySQL**.
- Sequence management (e.g., `DROP SEQUENCE`) may require `CASCADE` due to dependency tracking, which is not a concern in MySQL’s simpler model.

**DuckDB Syntax Examples**:
```sql
-- Create a sequence
CREATE SEQUENCE id_sequence START 1;

-- Use it in a table for auto-increment-like behavior
CREATE TABLE orders (
    id INTEGER PRIMARY KEY DEFAULT nextval('id_sequence'),
    name TEXT
);

-- Insert without specifying id
INSERT INTO orders (name) VALUES ('Test Order');

-- Get next sequence value directly
SELECT nextval('id_sequence');
```

**Title**: 4.3.2 Semantic Difference Between Empty String ('') and NULL  
**Content**:  
In DuckDB, the empty string `''` is also treated as a distinct, valid string value and is **not equivalent to `NULL`**, aligning with MySQL’s behavior in this specific regard. DuckDB represents string literals using single quotes (`'...'`), and `''` denotes a zero-length string of type `STRING_LITERAL` (which can be implicitly converted to `VARCHAR`). The `NULL` literal, by contrast, is explicitly denoted with the keyword `NULL` and represents the absence of a value.

However, there are **dialect and behavioral differences** worth noting:

- **Unlike MySQL**, DuckDB enforces stricter type semantics through its literal typing system (e.g., `STRING_LITERAL` vs. `VARCHAR`). While `''` is a valid non-`NULL` string, operations involving it may behave differently due to DuckDB’s implicit conversion rules.
- DuckDB allows implicit conversion from `STRING_LITERAL` (including `''`) to other types (e.g., dates or numbers) during parsing, but **explicitly typed `VARCHAR` values cannot be implicitly converted**—a nuance not present in MySQL.
- Both systems distinguish `''` from `NULL`, but DuckDB’s type system makes this distinction more rigid in binding contexts.

**DuckDB Syntax Examples**:
```sql
-- Empty string is NOT NULL
SELECT '' IS NULL;        -- Returns false
SELECT '' = '';           -- Returns true
SELECT LENGTH('');        -- Returns 0

-- NULL is distinct
SELECT NULL IS NULL;      -- Returns true
SELECT '' = NULL;         -- Returns NULL (unknown)

-- Implicit conversion works for string literals (including empty)
SELECT ''::INTEGER;       -- Fails at runtime (cannot cast empty string to int)
SELECT '5'::INTEGER;      -- Succeeds (5)
```

**CRITICAL**: While both MySQL and DuckDB treat `''` and `NULL` as semantically distinct, **DuckDB’s literal typing system introduces stricter compile-time binding rules** that affect how string literals (including empty ones) interact with other types—unlike MySQL, which applies more permissive automatic conversions in many contexts.

**Title**: Syntax Rules for GROUP BY Queries under sql_mode=only_full_group_by

**Content**:  
DuckDB enforces a strict and standards-compliant interpretation of GROUP BY semantics that aligns closely with the intent of MySQL’s only_full_group_by mode—but with key dialect differences and enhanced ergonomics.

Unlike MySQL, **DuckDB does not have a configurable sql_mode**, and its GROUP BY behavior is always "strict" by default: in any query with a GROUP BY clause, every column in the SELECT list must either be:
- A grouping column (i.e., explicitly listed in GROUP BY), or  
- Enclosed within an aggregate function (e.g., SUM(), COUNT(), MAX(), etc.).

This means DuckDB **automatically enforces functional dependency rules** similar to MySQL’s only_full_group_by, but without requiring mode configuration. However, **DuckDB does not provide a direct equivalent to MySQL’s ANY_VALUE()** function. Instead, if you need to select a representative non-grouping value, you must use an explicit aggregate like MIN(), MAX(), or FIRST() (a DuckDB extension).

A major **dialect difference** is DuckDB’s support for **GROUP BY ALL**, which automatically groups by all non-aggregate columns in the SELECT list. This eliminates redundancy and reduces errors—something MySQL cannot do. For example:

```sql
-- DuckDB: valid and concise
SELECT department, location, AVG(salary)
FROM employees
GROUP BY ALL;
-- Equivalent to: GROUP BY department, location
```

In contrast, MySQL would require explicitly listing both department and location in GROUP BY, or wrapping one in ANY_VALUE().

Additionally, **if a query contains aggregate functions but no GROUP BY clause**, DuckDB treats it as a scalar aggregation over the entire table—and **only allows aggregate expressions or literals in the SELECT list**. Attempting to select a bare column (e.g., SELECT id, COUNT(*) FROM users) results in an error, just like MySQL’s error 1140.

**Examples**:

✅ Valid in DuckDB:
```sql
SELECT city, COUNT(*) FROM addresses GROUP BY city;
SELECT department, MAX(salary) FROM employees GROUP BY department;
SELECT city, street_name, AVG(income) FROM addresses GROUP BY ALL;
```

❌ Invalid in DuckDB (and will error):
```sql
SELECT id, COUNT(*) FROM users;  -- Error: id is not aggregated and no GROUP BY
SELECT department, location, MAX(salary) FROM employees GROUP BY department;  -- Error: location not in GROUP BY and not aggregated
```

**CRITICAL DIFFERENCES**:
- **No ANY_VALUE()**: DuckDB lacks MySQL’s ANY_VALUE(); use FIRST(), MIN(), or MAX() instead.
- **GROUP BY ALL**: A DuckDB-specific convenience feature with no MySQL equivalent.
- **Always strict**: DuckDB enforces full group-by compliance by default—no mode toggling needed.
- **No silent fallback**: Unlike older MySQL versions (without only_full_group_by), DuckDB never permits ambiguous non-aggregated columns.

**Title**: 5.10 Basic Syntax Rules for UNION Statements

**Content**:  
DuckDB supports standard `UNION` and `UNION ALL` operations with behavior largely aligned with SQL standards and similar to MySQL in core aspects: both require the same number of columns across subqueries when using positional `UNION`, perform implicit type coercion where possible, and apply set semantics (deduplication) for `UNION` versus bag semantics (no deduplication) for `UNION ALL`.

However, **DuckDB introduces a significant dialect extension not found in MySQL**: `UNION [ALL] BY NAME`. This variant aligns columns by name rather than position, does **not** require matching column counts, and fills missing columns with `NULL`. This offers greater flexibility for combining heterogeneous schemas.

Additionally, unlike MySQL, DuckDB also supports `INTERSECT` and `EXCEPT` (both with and without `ALL`), which are not part of MySQL’s feature set.

**CRITICAL Differences**:
- **Unlike MySQL**, DuckDB allows `UNION BY NAME`, which unions tables by column names and tolerates differing column counts.
- **Unlike MySQL**, DuckDB fully implements `INTERSECT` and `EXCEPT` with both set and bag semantics.
- Both systems enforce equal column counts for positional `UNION`, but DuckDB’s type coercion may differ slightly in edge cases due to its stricter type system (though it still attempts implicit casts like MySQL).

**DuckDB Syntax Examples**:

1. **Standard UNION (positional, deduplicated)**:
```sql
SELECT 'Tallest Player' AS type, AVG(finishing) AS avg_fin FROM players WHERE height = (SELECT MAX(height) FROM players)
UNION
SELECT 'Shortest Player' AS type, AVG(finishing) AS avg_fin FROM players WHERE height = (SELECT MIN(height) FROM players);
```

2. **UNION ALL (positional, retains duplicates)**:
```sql
SELECT id FROM team_a
UNION ALL
SELECT id FROM team_b;
```

3. **UNION BY NAME (column-name-based, flexible schema)**:
```sql
SELECT city, country FROM capitals
UNION BY NAME
SELECT city, degrees FROM weather;
-- Result includes columns: city, country, degrees; missing values become NULL
```

4. **Derived table with UNION (alias required, same as MySQL)**:
```sql
SELECT COUNT(*) FROM (
    SELECT user_id FROM orders_2023
    UNION
    SELECT user_id FROM orders_2024
) AS all_users;
```

**Title**: Cross-Database Function Compatibility Differences

**Content**:  
DuckDB provides a rich set of built-in date functions that often align with or extend beyond SQL standard and other database dialects. Unlike MySQL—which strictly enforces its own function namespace and rejects non-MySQL functions with error 1305—DuckDB supports several functions commonly found in SQLite and PostgreSQL, including direct equivalents for some "incompatible" functions mentioned in the MySQL rule.

**CRITICAL Differences / Dialect Features**:
- **Unlike MySQL**, DuckDB **natively supports** `julian(date)` (equivalent to SQLite’s `JULIANDAY()`) and `strftime(date, format)` (same name as SQLite, but parameter order matches PostgreSQL/SQLite, not MySQL’s `DATE_FORMAT()`).
- DuckDB **does not have an `IIF()` function**, but it **fully supports standard SQL `CASE WHEN`** and also provides a ternary-like `IF(condition, true_value, false_value)` function—similar to MySQL’s `IF()`.
- DuckDB’s `date_diff()` (aliased as `datediff`) behaves differently from MySQL’s `DATEDIFF()`:  
  - MySQL’s `DATEDIFF(date1, date2)` returns days only.  
  - DuckDB’s `date_diff('day', date1, date2)` is explicit about the unit and supports multiple intervals (e.g., `'month'`, `'year'`).
- DuckDB **does not throw an error for “unknown” functions from other dialects by default**, but since it doesn’t implement SQLite/PostgreSQL-specific functions unless they are part of its own catalog, using truly unsupported functions will result in an error—though the error message differs from MySQL’s 1305.

**DuckDB Syntax Examples**:
```sql
-- Equivalent to SQLite's JULIANDAY()
SELECT julian(DATE '1992-09-20');  -- Returns 2448886.0

-- Equivalent to SQLite's STRFTIME (note: format string second)
SELECT strftime(DATE '1992-01-01', '%Y-%m-%d');  -- Returns '1992-01-01'

-- Conditional logic (like MySQL IF or SQLite IIF)
SELECT IF(score > 60, 'pass', 'fail') FROM (VALUES (70), (50)) t(score);
-- Or using CASE
SELECT CASE WHEN score > 60 THEN 'pass' ELSE 'fail' END FROM (VALUES (70), (50)) t(score);
```

Dialect Feature: Interval Representation and Arithmetic with Three Basis Units

DuckDB represents INTERVALs using three independent basis units—months, days, and microseconds—to correctly handle calendar irregularities (e.g., variable month lengths and DST-induced day lengths). This differs from many other databases (like PostgreSQL or MySQL), which often use a simpler two-component model (e.g., months + microseconds or just total seconds) or normalize intervals differently.

Key differences:

1. **Three-component internal storage**: Unlike systems that store intervals as a single scalar (e.g., total seconds) or only two components, DuckDB preserves months, days, and microseconds separately. This affects both arithmetic and comparison semantics.

2. **Interval comparisons use fixed conversions**: For equality and ordering, DuckDB converts months to 30 days and days to 24 hours (i.e., assumes all months = 30 days, all days = 24 hours). This leads to non-intuitive results:
   ```sql
   INTERVAL 30 DAYS = INTERVAL 1 MONTH  -- TRUE in DuckDB
   ```
   But when added to dates:
   ```sql
   DATE '2020-01-01' + INTERVAL 30 DAYS  -- → '2020-01-31'
   DATE '2020-01-01' + INTERVAL 1 MONTH  -- → '2020-02-01'
   ```
   These are not equal—highlighting that comparison ≠ functional equivalence.

3. **Subtracting DATEs returns INTEGER, not INTERVAL**: 
   ```sql
   DATE '2020-02-01' - DATE '2020-01-01'  -- Returns 31 (INTEGER)
   ```
   In contrast, PostgreSQL returns an INTERVAL for the same operation.

4. **Adding INTERVAL to DATE yields TIMESTAMP**: Even if the interval has no time component, DuckDB promotes DATE + INTERVAL to TIMESTAMP:
   ```sql
   DATE '2000-01-01' + INTERVAL 1 YEAR  -- Returns TIMESTAMP '2001-01-01 00:00:00'
   ```
   Other databases (e.g., PostgreSQL) return a DATE in such cases.

5. **datepart() splits microseconds into hour/minute/microsecond—but not seconds**: The omission of a dedicated "second" component in the core decomposition is unusual; seconds must be derived from microseconds.

These behaviors reflect DuckDB’s design choice to prioritize calendar-aware date arithmetic over simple linear time models, diverging from standard SQL and common implementations in PostgreSQL, MySQL, and others.

Dialect Feature: Friendly SQL Extensions in DuckDB

DuckDB introduces numerous syntactic extensions and conveniences—collectively called “Friendly SQL”—that deviate from standard SQL and differ from traditional databases like PostgreSQL or MySQL. Many of these features either simplify common tasks or introduce entirely new syntax not found elsewhere (or only recently adopted by others after DuckDB pioneered them).

Key dialect differences include:

1. **FROM-first shorthand**:  
   `FROM tbl` is equivalent to `SELECT * FROM tbl`.  
   → Standard SQL requires an explicit `SELECT *`.

2. **GROUP BY ALL / ORDER BY ALL**:  
   `SELECT a, b, sum(c) FROM t GROUP BY ALL` automatically groups by non-aggregate columns (`a`, `b`).  
   → Standard SQL requires listing all non-aggregate columns explicitly in `GROUP BY`. PostgreSQL and MySQL do not support `GROUP BY ALL`.

3. **SELECT * EXCLUDE / REPLACE**:  
   `SELECT * EXCLUDE(col)` or `SELECT * REPLACE(col + 1 AS col)` modifies star expansion.  
   → Not part of standard SQL; supported only in newer engines (e.g., BigQuery, Snowflake), but not in MySQL or PostgreSQL.

4. **INSERT ... BY NAME**:  
   Matches columns by name rather than position during insertion.  
   → Standard SQL and most databases (including PostgreSQL and MySQL) rely on positional matching.

5. **UNION BY NAME**:  
   Aligns columns by name instead of position in `UNION`.  
   → Standard SQL uses positional alignment; PostgreSQL and MySQL lack this feature.

6. **Prefix aliases**:  
   `x: 42` instead of `42 AS x`.  
   → Non-standard syntax; not supported in other major databases.

7. **Percentage-based LIMIT**:  
   `LIMIT 10%` returns 10% of rows.  
   → Not valid in standard SQL or in PostgreSQL/MySQL.

8. **Column aliases usable in WHERE/GROUP BY/HAVING**:  
   `SELECT x + 1 AS y FROM t WHERE y > 5` is allowed.  
   → Standard SQL and PostgreSQL forbid referencing SELECT aliases in WHERE (only in HAVING for aggregates); MySQL allows it in some contexts but inconsistently.

9. **Trailing commas**:  
   Allowed in SELECT lists and array literals: `SELECT a, b, FROM t` or `[1, 2,]`.  
   → Standard SQL and most databases reject trailing commas.

10. **Top-N aggregate functions**:  
    `SELECT max(val, 3) FROM t GROUP BY grp` returns top-3 values per group as an array.  
    → No equivalent in standard SQL or in PostgreSQL/MySQL without window functions.

These features collectively make DuckDB’s SQL dialect significantly more expressive and concise than standard SQL or traditional RDBMS implementations, representing clear dialect differences rather than mere standard functionality.

Dialect Feature: DuckDB's Extended `IN` Operator with List, Map, and String Semantics

Dialect Feature: DuckDB’s Pattern Matching Operators and PostgreSQL Compatibility Differences

DuckDB supports multiple pattern matching operators—LIKE, ILIKE, SIMILAR TO, GLOB, and POSIX-style regular expressions—but implements them with notable differences from standard SQL and other databases like PostgreSQL:

1. **PostgreSQL-style symbolic operators**:
   - DuckDB supports `~~` (LIKE), `!~~` (NOT LIKE), `~~*` (ILIKE), and `!~~*` (NOT ILIKE) for PostgreSQL compatibility.
   - However, unlike PostgreSQL, DuckDB does **not** treat `~` as equivalent to `SIMILAR TO`. In PostgreSQL, `~` means POSIX regex match (not SIMILAR TO), but the documentation explicitly notes that in DuckDB, `~` maps to `regexp_full_match`, and `~*` (case-insensitive regex) is **not supported**.

2. **GLOB operator**:
   - DuckDB includes a non-standard `GLOB` operator (also usable as `~~~`) using shell-like wildcards (`*`, `?`, `[...]`), which is **not part of standard SQL** and absent in MySQL/PostgreSQL.
   - Its globbing semantics follow Python’s `glob`, not Unix shells: notably, `**/file` does **not** match top-level files (unlike Bash/Zsh), which is a key behavioral difference from shell globbing and some other systems.

3. **SIMILAR TO behavior**:
   - While `SIMILAR TO` is part of SQL:1999, its support varies. DuckDB implements it with full-string matching (like LIKE), but explicitly diverges from PostgreSQL by **not equating `~` to `SIMILAR TO`**—in fact, PostgreSQL doesn’t use `SIMILAR TO` with `~` at all; `~` is for POSIX regex.

4. **Case-insensitive matching**:
   - DuckDB supports `ILIKE` (standard in PostgreSQL but **not in MySQL or standard SQL**), and extends it with `ESCAPE` clauses and symbolic forms (`~~*`), enhancing PostgreSQL compatibility while differing from MySQL (which uses `LIKE` with collations or `REGEXP` for case control).

Examples highlighting differences:
```sql
-- PostgreSQL-compatible symbols (DuckDB-only among many DBs)
SELECT 'abc' ~~ 'a%';      -- true (same as LIKE)
SELECT 'ABC' ~~* '%c';     -- true (ILIKE)

-- GLOB is DuckDB-specific
SELECT 'best.txt' GLOB '*.txt';        -- true
SELECT 'best.txt' ~~~ '*.txt';         -- same as above

-- DuckDB's ~ means regexp_full_match, NOT SIMILAR TO
SELECT 'abc' ~ '.*(b|d).*';            -- true (full regex match)

-- But ~* is unsupported (PostgreSQL supports it for case-insensitive regex)
-- This would fail in DuckDB but work in PostgreSQL
```

These features show DuckDB extending SQL with PostgreSQL-inspired syntax while introducing unique behaviors (like GLOB and Python-style glob semantics) not found in standard SQL, MySQL, or even PostgreSQL in the same form.

DuckDB supports a USING SAMPLE clause that appears immediately after the FROM clause (including after joins) but before WHERE or aggregation—unlike standard SQL, which does not define a SAMPLE clause at all, and unlike databases like PostgreSQL or SQL Server that either lack native sampling or implement it via TABLESAMPLE in a different syntactic position.

- **Syntax**: DuckDB uses USING SAMPLE after FROM, whereas PostgreSQL (and SQL Standard) uses TABLESAMPLE directly after the table name (e.g., FROM addresses TABLESAMPLE BERNOULLI (1)).

- **Flexibility**: DuckDB allows sampling by percentage or fixed row count (e.g., USING SAMPLE 10 ROWS), and supports sampling methods like bernoulli inline.

```sql
-- SELECT * FROM addresses TABLESAMPLE BERNOULLI (1);
```

This represents a dialect difference in both syntax and scoping of sampling operations compared to other SQL databases.

Dialect Feature: CREATE MACRO (Scalar and Table Macros with Overloading and Default Parameters)

DuckDB introduces a non-standard SQL extension called CREATE MACRO, which allows users to define both scalar and table-valued macros that are expanded at query planning time. This differs significantly from standard SQL and most other databases (like PostgreSQL or MySQL), which rely on user-defined functions (UDFs) written in procedural languages or external code, rather than textual macro substitution.

Key differences from other databases:

1. **Macro Expansion vs. Function Execution**: Unlike traditional SQL functions, DuckDB macros are not executed as runtime routines but are textually expanded before query execution. This enables powerful compile-time expression composition without the overhead of function calls.

2. **Table Macros**: DuckDB supports table macros using AS TABLE syntax, allowing parameterized queries that return tables—similar in spirit to PostgreSQL’s set-returning functions or SQL Server’s table-valued functions—but implemented via macro expansion rather than procedural logic.

3. **Overloading by Arity and Type**: DuckDB allows overloading macros based on the number or types of parameters in a single CREATE MACRO statement (e.g., defining both add(a, b) and add(a, b, c) together). Most SQL databases do not support function overloading in pure SQL without procedural extensions (e.g., PostgreSQL allows it in PL/pgSQL, but not via simple SQL definitions).

4. **Default Parameters with := Syntax**: DuckDB macros support default values using := (e.g., b := 5), and allow out-of-order named arguments (e.g., triple_add(40, c := 1, b := 1)). While PostgreSQL supports default parameters in functions, it uses =, not :=, and MySQL does not support default parameters in SQL-level functions at all.

5. **Schema-bound and Aliased as FUNCTION**: DuckDB allows CREATE FUNCTION as an alias for CREATE MACRO, blurring the line between macros and functions—a design choice not found in standard SQL or other major databases.

```sql
-- Scalar macro with default parameter

-- Table macro

    SELECT col1_value AS column1, col2_value AS column2;

-- Overloaded macro in one statement
CREATE MACRO add_x
    (a, b) AS a + b,
    (a, b, c) AS a + b + c;
```

This feature is a DuckDB-specific dialect extension that changes how reusable logic is defined and optimized, diverging from standard SQL and the UDF models of PostgreSQL, MySQL, and others.

Dialect Feature: INSERT ... BY NAME and Conflict Handling Syntax

DuckDB introduces non-standard extensions to the INSERT statement that differ from common SQL dialects like PostgreSQL, MySQL, and standard SQL:

1. **INSERT ... BY NAME**:  
   DuckDB supports an explicit `BY NAME` clause that matches columns by name rather than position when inserting from a SELECT. This is not part of standard SQL and is not supported in PostgreSQL or MySQL. For example:
   ```sql
   INSERT INTO tbl BY NAME (SELECT 42 AS b, 32 AS a);
   ```
   Here, values are inserted into columns `a` and `b` based on column aliases in the SELECT, regardless of their order. Standard SQL requires either positional matching or explicit column lists without the `BY NAME` modifier.

2. **SQLite-style conflict resolution syntax (`INSERT OR IGNORE` / `INSERT OR REPLACE`)**:  
   DuckDB adopts SQLite’s shorthand syntax for handling constraint violations:
   - `INSERT OR IGNORE INTO ...` ≡ `INSERT INTO ... ON CONFLICT DO NOTHING`
   - `INSERT OR REPLACE INTO ...` ≡ `INSERT INTO ... ON CONFLICT DO UPDATE SET col = EXCLUDED.col` for all columns  
   While PostgreSQL supports `ON CONFLICT DO NOTHING/UPDATE` (UPSERT), it does **not** support the `INSERT OR IGNORE/REPLACE` syntax—this is specific to SQLite and now DuckDB. MySQL uses `INSERT IGNORE` and `ON DUPLICATE KEY UPDATE`, which are syntactically different.

3. **RETURNING clause with arbitrary expressions**:  
   Although PostgreSQL also supports `RETURNING`, DuckDB extends it to allow arbitrary non-aggregate expressions alongside `*`, such as:
   ```sql
   INSERT INTO t2 SELECT 2, 3 RETURNING *, i * j AS i_times_j;
   ```
   While PostgreSQL allows expressions in `RETURNING`, the combination with `*` and computed columns in this flexible way aligns more closely with DuckDB’s analytical orientation and is not universally portable.

These features represent **dialect differences**, as they either adopt SQLite-specific syntax (`OR IGNORE`, `OR REPLACE`) or introduce novel extensions (`BY NAME`) not found in standard SQL or major databases like PostgreSQL or MySQL.

Dialect Feature: DuckDB's Simplified UNPIVOT Syntax and COLUMNS Expression Support

DuckDB extends the SQL standard UNPIVOT functionality with a simplified, more intuitive syntax and powerful dynamic column selection using the COLUMNS expression—features not found in most other SQL databases like PostgreSQL or MySQL (which often lack native UNPIVOT support entirely).

Key differences from standard SQL and other databases:

1. **Simplified UNPIVOT Syntax**:  
   DuckDB allows a spreadsheet-style UNPIVOT syntax that is not part of the SQL standard:
   ```sql
   UNPIVOT dataset
   ON columns
   INTO
       NAME name_col
       VALUE value_col;
   ```
   This contrasts with the SQL Standard syntax used by Oracle or SQL Server:
   ```sql
   SELECT ...
   FROM table
   UNPIVOT (value_col FOR name_col IN (col1, col2, ...));
   ```
   Notably, DuckDB permits UNPIVOT as a top-level statement (not just within FROM), which deviates from standard usage.

2. **COLUMNS Expression for Dynamic Unpivoting**:  
   DuckDB supports the COLUMNS(* EXCLUDE (...)) construct inside UNPIVOT to dynamically select columns:
   ```sql
   UNPIVOT monthly_sales
   ON COLUMNS(* EXCLUDE (empid, dept))
   INTO NAME month VALUE sales;
   ```
   This capability—automatically excluding or including columns via pattern matching—is unique to DuckDB and not available in PostgreSQL, MySQL, or even most commercial databases that implement UNPIVOT.

3. **UNPIVOT as Standalone Statement or in Subqueries Without SELECT**:  
   DuckDB allows UNPIVOT to be used directly in a CTE or subquery without wrapping it in a SELECT:
   ```sql
   WITH t AS (UNPIVOT ...)
   SELECT * FROM t;
   ```
   In standard SQL, table-valued operations like UNPIVOT must appear in the FROM clause of a SELECT. DuckDB’s flexibility here is non-standard.

4. **Support for Expressions in UNPIVOT Columns**:  
   DuckDB permits expressions (e.g., casts, arithmetic) on individual columns within the ON clause:
   ```sql
   UNPIVOT (SELECT 42 AS col1, 'woot' AS col2)
   ON (col1 * 2)::VARCHAR, col2;
   ```
   Most databases restrict UNPIVOT to raw column names only.

These extensions make DuckDB’s UNPIVOT significantly more flexible and user-friendly than implementations in other systems, constituting clear dialect differences from both standard SQL and common database engines.

Dialect Feature: DuckDB's Limited and Non-Standard VACUUM Statement

Unlike PostgreSQL—where VACUUM is a core maintenance command that reclaims storage and optionally updates table statistics—DuckDB’s VACUUM statement is only partially implemented and behaves differently:

- In DuckDB, VACUUM and VACUUM ANALYZE with no arguments are no-ops.
- DuckDB uniquely allows VACUUM my_table(my_column) or VACUUM ANALYZE my_table(my_column) to recompute distinct-value statistics for a specific column—a syntax not found in PostgreSQL or standard SQL.
- Crucially, DuckDB does not support VACUUM FULL (which in PostgreSQL rewrites the table and reclaims disk space), and explicitly throws a "Not implemented Error" for it.
- DuckDB’s VACUUM does not reclaim disk space at all, contrary to the primary purpose of VACUUM in PostgreSQL.

This partial, non-standard implementation is explicitly acknowledged in DuckDB’s documentation as being “mostly provided for PostgreSQL-compatibility” but “not consistent with PostgreSQL semantics.”
