1.6.3 NULL Handling Details in LEFT JOIN
-- MySQL:
   Method:
      NULL retention rule: LEFT JOIN forcibly retains all records from the left table, associated fields return NULL when no match in right table; Need to fill NULLs via COALESCE(right_table_field, default_value) (e.g., convert NULL to 0 or "No Data");
      Difference from INNER JOIN: INNER JOIN only returns matching records from both tables, LEFT JOIN includes unmatched records from left table (right table fields are NULL);
      Performance optimization: Right table join column needs index (to avoid full table scan), left table conditions placed in WHERE clause (filter data early), right table filter conditions must be placed in ON clause (otherwise implicitly converted to INNER JOIN).
  eg:
      Basic LEFT JOIN retaining left table (corresponding to issue 27 scenario):
      SELECT s.school_id, s.name, ss.AvgScrWrite FROM schools s LEFT JOIN satscores ss ON s.school_id = ss.school_id;
      COALESCE filling NULL values:
      SELECT s.name, COALESCE(ss.AvgScrWrite, 0) AS avg_write_score FROM schools s LEFT JOIN satscores ss ON s.school_id = ss.school_id;
      Right table condition in ON (avoid conversion to INNER JOIN):
      SELECT s.name, ss.AvgScrWrite FROM schools s LEFT JOIN satscores ss ON s.school_id = ss.school_id AND ss.year = 2023;

5.8 Syntax Rules for GROUP BY Queries under sql_mode=only_full_group_by

-- MySQL:
   Method:
      Core Constraint: The only_full_group_by mode enforces that GROUP BY queries must follow the rule: "Columns in the SELECT list must be either grouping columns in the GROUP BY clause, or wrapped by aggregate functions (MAX/MIN/SUM/ANY_VALUE, etc.)". If there is no GROUP BY clause (aggregate query without GROUP BY), the SELECT list cannot contain non-aggregated columns;
      Error Scenario: Violating the constraint throws error 1140 ("Mixing of GROUP columns with no GROUP columns is illegal if there is no GROUP BY clause") or error 1055 ("Expression #N of SELECT list is not in GROUP BY clause and contains nonaggregated column ... which is not functionally dependent on columns in GROUP BY clause");
      Solutions: ① Add the non-aggregated column to the GROUP BY clause; ② Wrap the non-aggregated column with an aggregate function (e.g., ANY_VALUE(non_aggregated_column)); ③ Temporarily disable only_full_group_by (SET sql_mode=(SELECT REPLACE(@@sql_mode,'ONLY_FULL_GROUP_BY','')), not recommended for production).
   eg:
      Example violating the rule (corresponding to problem scenario 1404):
      SELECT id, COUNT(*) FROM users; (No GROUP BY but SELECT contains non-aggregated column id, triggers error 1140)
      Solution 1: Add GROUP BY column
      SELECT id, COUNT(*) FROM users GROUP BY id;
      Solution 2: Wrap non-aggregated column with ANY_VALUE
      SELECT ANY_VALUE(id), COUNT(*) FROM users;
      Correct example of GROUP BY query:
      SELECT department, MAX(salary), ANY_VALUE(location) FROM employees GROUP BY department; (location is not a GROUP BY column, wrapped with ANY_VALUE)

5.9 Mandatory Rule: Derived Table (Table-level Subquery) Must Have an Alias

-- MySQL:
   Method:
      Mandatory Constraint: Derived tables (table-level subqueries) in the FROM clause must specify an alias using AS (the AS keyword can be omitted but explicit writing is recommended). Otherwise, it triggers error 1248 ("Every derived table must have its own alias"); Even if the derived table is only a temporary result set, an alias is required for identification;
      Error Scenario: Using a subquery directly after FROM without an alias (e.g., SELECT * FROM (SELECT id FROM users)), causing syntax parsing failure;
      Solution: Add an alias for the derived table (AS t/t). The alias can be custom (e.g., t1/temp).
   eg:
      Error example (triggers error 1248, corresponding to problem scenarios 1058/1107):
      SELECT COUNT(*) FROM (SELECT user_id FROM orders WHERE amount > 1000);
      Correct example (add alias):
      SELECT COUNT(*) FROM (SELECT user_id FROM orders WHERE amount > 1000) AS t;
      Abbreviated form omitting AS (still legal):
      SELECT t.user_id FROM (SELECT id AS user_id FROM users) t;

5.10 Basic Syntax Rules for UNION Statements

-- MySQL:
   Method:
      Core Rules:
      The number of columns in all subqueries combined by UNION must be exactly the same (different column count triggers error 1222: "The used SELECT statements have a different number of columns");
      Corresponding columns should have compatible data types (MySQL supports implicit conversion, e.g., INT and VARCHAR numeric strings can be merged);
      UNION automatically removes duplicates (merges duplicate rows), UNION ALL retains all rows (no deduplication overhead, better performance);
      When using UNION within a derived table, an alias must be specified for the entire union (following the derived table alias rule).
   eg:
      Basic UNION (merging average finishing for tallest/shortest players, corresponding to problem scenario 1058):
      SELECT 'Tallest Player' AS type, AVG(finishing) AS avg_fin FROM players WHERE height = (SELECT MAX(height) FROM players) UNION SELECT 'Shortest Player' AS type, AVG(finishing) AS avg_fin FROM players WHERE height = (SELECT MIN(height) FROM players);
      UNION ALL retaining duplicate rows:
      SELECT id FROM team_a UNION ALL SELECT id FROM team_b; (Retains duplicate ids from both tables)
      UNION nested in derived table (requires alias):
      SELECT COUNT(*) FROM (SELECT user_id FROM orders_2023 UNION SELECT user_id FROM orders_2024) AS all_users;

5.12 Format Consistency and Boundary Handling for Date Field Filtering

-- MySQL:
   Method:
      Format Specification: DATE/DATETIME types only support YYYY-MM-DD (or YYYY-MM-DD HH:MM:SS) as legal filter formats, do not directly support YYYY/MM/DD (need to use STR_TO_DATE to convert to standard format); For TEXT type stored dates, if the format is YYYY-MM-DD, direct comparison is possible; non-standard formats need to be unified first;
      Type and Filter Syntax: DATE types use equality/range comparisons (=/BETWEEN). TEXT types with non-standard formats need to use LIKE (e.g., date_text LIKE '1993-07%') or convert before comparison;
      Boundary Handling: Date range queries need to pay attention to closed interval boundaries (e.g., querying data for July 1993 requires date BETWEEN '1993-07-01' AND '1993-07-31'); For TEXT type dates stored as 1993/7/5, conversion is needed: STR_TO_DATE(date_text, '%Y/%m/%d') = '1993-07-05';
      Sorting Compatibility: Sort directly by the date field (ORDER BY date DESC), no need for extra functions (like JULIANDAY).
   eg:
      DATE type standard format filtering (corresponding to loan.date scenario):
      SELECT * FROM financial WHERE loan.date = '1993-07-05';
      TEXT type non-standard format conversion:
      SELECT * FROM logs WHERE STR_TO_DATE(date_text, '%Y/%m/%d') = '1993-07-05';
      Date range boundary handling:
      SELECT * FROM orders WHERE create_date BETWEEN '1993-07-01' AND '1993-07-31';
      Direct sorting:
      SELECT * FROM users ORDER BY dob DESC;

<Sub-category>:
